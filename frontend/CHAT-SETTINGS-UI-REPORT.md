## API layer

`src/api/types.ts` now exports the generated #80 types:

- `ChatCoverRequest`, `ChatPermissions`, `ChatRolePermissions`, `ChatPermissionsUpdate`,
  `ChatRolePermissionsUpdate`, `ChatPin`, `ChatPinList`
- `ChatJoinPolicy`, `ChatPermissionRole`, `ChatPermissionKey`
- the existing `ChatUpdateRequest` is documented as carrying `cover_file_id`,
  `read_only`, `visibility`, `join_policy` and `rights`.

`src/api/endpoints.ts` adds every #80 operation:

| Method                                                 | Endpoint                                | UI use                      |
| ------------------------------------------------------ | --------------------------------------- | --------------------------- |
| `listChats(workspaceId, archived?)`                    | `GET /workspaces/{id}/chats?archived=`  | personal archive list       |
| `setChatCover` / `deleteChatCover`                     | `POST` / `DELETE /chats/{id}/cover`     | pick an existing chat image |
| `getChatPermissions` / `updateChatPermissions`         | `GET` / `PATCH /chats/{id}/permissions` | rights matrix               |
| `archiveChat` / `unarchiveChat`                        | `POST /chats/{id}/archive               | unarchive`                  | user-local archive |
| `deleteOwnChat`                                        | `DELETE /chats/{id}`                    | OWNER soft delete           |
| `listChatPins` / `pinChatMessage` / `unpinChatMessage` | `/chats/{id}/pins`                      | pin panel + message action  |

`deleteOwnChat` is named separately from the pre-existing platform-admin
`deleteChat(chatId)`; the contract operation id is the same, the intents are not.
`listChats` only sends `archived=true`; absent/false is the documented main list.

## Store (`src/store/chatStore.ts`)

New server-confirmed state, each with generation guards so a stale response cannot
overwrite a newer chat:

- `chatPermissions` — matrix, loading/error, `saving/saved/error`
- `chatCover` — existing image candidates (`GET /files?chat_id&kind=IMAGE`), set/remove action state
- `chatPins` — metadata list, per-message pending/error, `limitReached`
- `chatArchive`, `chatDeletion` — action state for the danger zone
- `archivedChats` — the caller-local archive, kept out of `chats`

Actions: `loadChatPermissions`, `saveChatPermissions`, `loadChatCoverImages`,
`setChatCover`, `removeChatCover`, `loadChatPins`, `pinMessage`, `unpinMessage`,
`loadArchivedChats`, `archiveChat`, `unarchiveChat`, `deleteOwnChat`, plus `clear*`
helpers. There is **no optimistic update**: summaries are replaced only from the
returned `Chat`, `204` is applied to the local list, and errors stay next to the action.

Helpers used by the UI:

- `defaultChatPermissions()` / `chatPermissionAllowed()` — mirrors the backend defaults
  (OWNER all-true, ADMIN all-true, MODERATOR without `change_info`, MEMBER without
  `invite_members`/`pin_messages`/`change_info`, GUEST read/write only).
- `chatActorRole(chatId)` — the viewer's channel role from the member directory.
- `canPinMessages(chatId)` — GROUP + managed + `pin_messages` (OWNER/ADMIN always).
- `canPostInChat(chatId)` — read-only denies every role except chat OWNER/ADMIN.
- `chatSummaryFromChat` now preserves `cover_file_id`, `read_only`, `join_policy`,
  `archived`; `toChatSummary` emits them too.

## Chat settings UI (`ChatSettingsDialog.tsx`)

**Main tab**

- Current cover is rendered from `cover_file_id` (lazily resolved through
  `GET /attachments/{id}/download-url`; a failure keeps the design static cover).
- “Заменить обложку” opens an in-dialog picker fed by
  `GET /files?chat_id=<id>&kind=IMAGE` and offers only `CLEAN`/`SKIPPED` images.
  Selecting one calls `POST /cover` with `{ file_id }`; “Удалить обложку” calls
  `DELETE /cover`. There is **no upload endpoint** in this flow. Empty/loading/error
  states and every translated server error (403/404/409/422/423) are shown.
- Read-only toggle, visibility (`PUBLIC`/`PRIVATE`) and join policy
  (`OPEN`/`INVITE_ONLY`/`CLOSED`) are sent in the same `PATCH /chats/{id}` as
  name/description. `PUBLIC` forces `OPEN` in the UI; switching away from `PUBLIC`
  downgrades `OPEN` to `INVITE_ONLY`. The form shows the honest “only owner/admin of
  the channel” note when the viewer cannot change structural settings.
- `DIRECT` has no structural section, no cover action and no delete card; `E2EE`
  keeps the read-only/visibility/join policy controls but rejects the cover with a
  dedicated explanation.

**Rights tab**

- Real 6-permission × 5-role matrix (`post_messages`, `invite_members`,
  `create_polls`, `start_calls`, `pin_messages`, `change_info` ×
  OWNER/ADMIN/MODERATOR/MEMBER/GUEST) rendered as an accessible table with a
  horizontally scrollable wrapper.
- OWNER is always checked and disabled; the server rejects an owner row.
- Loads with `GET /permissions`; loading/error/retry states; a MEMBER sees the
  matrix read-only with the server-computed values.
- Save sends only the changed role rights through `PATCH /permissions`; success
  replaces the matrix from the response, failure keeps the draft and shows
  `403`/`422` translations. Empty patches are never sent.

Name/description are editable by workspace OWNER/ADMIN **or** by a channel role with
`change_info`; `change_info` is therefore honest in the UI and not just a toggle.

**Danger tab**

- Archive/unarchive (user-local, DIRECT included) with pending/error state. Archiving
  the open chat closes the dialog and removes it from the main list.
- Leave (GROUP) and block/unblock (DIRECT) keep their existing confirm dialogs.
- Delete (GROUP only) is enabled only for the chat OWNER, requires an explicit
  destructive confirmation with the channel name, calls `DELETE /chats/{id}` and
  removes the chat/slices locally after `204`. Non-owners see why it is disabled.

## Pins

- `ChatDetails` gained a “Закреплённые сообщения” accordion: `GET /pins` on open,
  newest-first metadata list, author/loaded-message preview, “not in loaded history”
  fallback, retry, and an unpin button when the viewer has `pin_messages`.
- `MessageActions` gained a pin/unpin button. It appears only for GROUP + managed
  chats when the viewer has `pin_messages`; it toggles the pin and shows the server
  error inline. `409 CHAT_PIN_LIMIT` is translated as the 50-pin cap.
- Pins never expose content (contract is metadata only); E2EE and DIRECT get no pin
  affordance at all.

## Archived chats

- `Sidebar` has a separate “Архив” section. Opening it calls
  `GET /workspaces/{id}/chats?archived=true`; rows show the caller-local archived
  chats with an “Вернуть” action (`POST /unarchive`), count, loading/error/retry and
  an empty state. The main list is reloaded and the row disappears from the archive
  after a successful unarchive. Archive is never mixed into `chats`, so the normal
  “active chat” and unread logic is unaffected.

## Read-only send guard

- `Composer` and `StickerPicker` gained a `read_only` blocked reason with a dedicated
  honest note; the send button is disabled for non-manager roles.
- `ChatScreen` loads members/permissions for the active GROUP chat, so the guard and
  the pin affordance know the real channel role. Voice capture is also disabled and
  its completion path refuses to send in read-only mode.
- The server remains authoritative: `403 CHAT_READ_ONLY` is still translated if the
  UI state is stale. The MSW send handler enforces the same rule after an
  idempotency replay.

## Honest limitations / notes

- Cover candidates come from the file center, i.e. images already attached to
  messages in this chat. Unbound uploads are not offered by the contract, and there is
  no new upload endpoint. If a chat has no checked images the picker says so.
- The archived list supports listing and unarchiving; opening an archived chat from
  that list is not part of this slice (unarchive first).
- Pin rows show metadata plus a preview only when the message is in the loaded
  history; otherwise an explicit “not loaded” line is rendered.
- Archive is user-local and not reflected in `GET /sync` (backend scope); the sidebar
  reloads the list after archive/unarchive.
- No realtime fan-out for pin/unpin (backend scope); the acting tab updates from the
  API response and other tabs see it on the next pins reload.
