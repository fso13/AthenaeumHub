# ADR: решения по разделению монолита

> Формат: контекст → решение → альтернативы → последствия. Статусы: `proposed`, `accepted`, `superseded`.
> Все ADR относятся к [MICROSERVICES.md](MICROSERVICES.md) и [MIGRATION.md](MIGRATION.md).

## ADR-001: Chat и message — один сервис

**Статус:** proposed · **Дата:** 2026-11-25

**Контекст.** Отправка сообщения — одна транзакция: idempotency reservation, ACL чата, `seq` под row lock в `chat.chat_counters`, insert message + envelopes, outbox. Чат и сообщение масштабируются одинаково (PostgreSQL + CPU), нагрузка общая. E2EE-валидация требует устройств и чата в той же транзакции.

**Решение.** `chat` и `message` остаются одним сервисом `conversation` с одной БД. Граница — вокруг пары, не между ними.

**Альтернативы.**
- `chat` и `message` — отдельные сервисы: `seq` через распределённый lock или перенос в `message`; сага на счётчики; +1 сетевой hop в hot path; риск разрыва `seq`.
- `seq`-сервис: ещё один hop и точка отказа, выигрыша нет.

**Последствия.** Меньше гибкости в независимом масштабировании `chat`/`message`; зато сохраняются атомарность, p95 и порядок. Пересмотр — только по ADR при появлении реального разного профиля нагрузки.

## ADR-002: Kafka и transactional outbox

**Статус:** proposed

**Контекст.** Сейчас события — Spring `@TransactionalEventListener` + `LoggingEventPublisher`; outbox помечается published, но никуда не публикуется. Горизонтальный realtime и асинхронные сервисы невозможны.

**Решение.** Kafka (или Redpanda) как event backbone; в БД каждого сервиса — `outbox`; relay через `SKIP LOCKED` (или Debezium); at-least-once; идемпотентные консьюмеры; DLQ.

**Альтернативы.** NATS JetStream (легче, но беднее экосистема и инструменты), RabbitMQ (нет удобного replay/партиций), синхронные вызовы (хуже изоляция).

**Последствия.** Нужны Schema Registry/JSON Schema, мониторинг lag, DLQ, retry-политики. Появляется эксплуатационная сложность, но без брокера разделение невозможно.

## ADR-003: Database per service

**Статус:** proposed

**Контекст.** 13 схем в одной БД, 93 FK между схемами, 60 `SECURITY DEFINER`-функций, одна Flyway-история. Схемы — не границы.

**Решение.** У каждого сервиса — своя БД и роль; никаких кросс-БД JOIN и FK. На старте — отдельная database в общем кластере PostgreSQL; физическое разделение — по мере роста/комплаенса.

**Альтернативы.** Shared DB с схемами (быстро, но распределённый монолит), shared DB с views (скрывает связность), «пока оставить FK» (блокирует независимые релизы).

**Последствия.** Нужны проверки целостности в коде, reconciliation, saga/outbox. Удаление 93 FK — отдельная программа работ ([MIGRATION.md §6](MIGRATION.md#6-удаление-93-fk)).

## ADR-004: REST/JSON для внутренних API, gRPC — позже

**Статус:** proposed

**Контекст.** Команда знает Spring MVC/Jackson; контракты уже OpenAPI; нагрузка на внутренние вызовы умеренная.

**Решение.** Внутренние API — REST/JSON под `/internal/v1/*`, mTLS, batch-эндпоинты. gRPC — только для измеренных hot path (например, ACL/envelopes), с отдельным ADR.

**Альтернативы.** Сразу gRPC (сложнее отладка, кодогенерация, меньше разработчиков), GraphQL (не для межсервисных вызовов), messaging-only (не для запросов).

**Последствия.** Проще старт и отладка; выше overhead JSON. При росте QPS на ACL/envelopes — точечно gRPC.

## ADR-005: Edge Gateway + тонкий BFF

**Статус:** proposed

**Контекст.** Клиент не должен знать топологию; нужна единая точка TLS/JWT/rate limit/CSRF; экраны требуют композиции (список чатов + последние сообщения + аватары).

**Решение.** Один deployable `edge` = Spring Cloud Gateway + BFF-контроллеры композиции. В edge нет доменных инвариантов; только маршрутизация, безопасность, DTO-агрегация.

**Альтернативы.** Чистый gateway без BFF (клиент делает N запросов), отдельный BFF-сервис (ещё один deployable), nginx + auth-фильтр (меньше возможностей).

**Последствия.** Edge становится критичным и должен масштабироваться; риск «ожирения» — контролируется ревью и ArchUnit-правилом «нет домена в edge».

## ADR-006: JWT на edge, mTLS внутри

**Статус:** proposed

**Контекст.** Сейчас JWT выпускается BFF/Keycloak, проверяется в монолите; cookie refresh — HttpOnly. Нужна единая аутентификация для 10 сервисов.

**Решение.** Пользовательский JWT проверяется на `edge` (JWKS, audience, exp, device binding); внутрь передаётся mTLS + `X-Actor-Id`, `X-Workspace-Id`, `X-Request-Id`, `X-Device-Id`. Сервисы не доверяют заголовкам извне. Access — 15 мин, refresh — HttpOnly cookie с ротацией.

**Альтернативы.** JWT в каждом сервисе (дублирование, рассинхрон ключей), opaque-токены + introspection (лишний hop), session-cookie в каждом сервисе (связанность).

**Последствия.** Нужны cert-manager/mTLS, NetworkPolicy, сервисные аккаунты. Отзыв сессии — через событие, а не мгновенно во всех сервисах (см. SLO revoke < 5 с).

## ADR-007: Аудит — асинхронно, через outbox

**Статус:** proposed

**Контекст.** Сейчас `AuditPort.append` пишет в `audit.*` в транзакции бизнес-операции. При выделении `audit` синхронная запись станет распределённой транзакцией и точкой отказа.

**Решение.** Каждый сервис пишет audit-событие в свой outbox; `audit` потребляет, строит hash chain, экспортирует в SIEM. At-least-once + дедуп по `event_id`; reconciliation-джоба.

**Альтернативы.** Синхронный append (latency, доступность), локальные audit-таблицы в каждом сервисе (сложная целостность), «писать только критичное» (не соответствует комплаенсу).

**Последствия.** Аудит становится eventually consistent (lag p95 < 5 с). Для break-glass/критичных действий — отдельный sync-канал с fallback и алертом.

## ADR-008: JSON Schema для событий

**Статус:** proposed

**Контекст.** События уже JSON; команда знает JSON Schema; Avro/Schema Registry добавляет инфраструктуру.

**Решение.** JSON Schema в `contracts/events/`, версия в envelope, CI-валидация producer/consumer, обратная совместимость в пределах major. Avro/Registry — при росте числа команд/языков.

**Альтернативы.** Avro + Registry (компактнее, строже, но +инфраструктура), Protobuf (кодогенерация, сложнее эволюция), без схем (хаос).

**Последствия.** Больше размер сообщений, слабее типизация; зато низкий порог входа и прозрачные диффы.

## ADR-009: Realtime выделяется первым

**Статус:** proposed

**Контекст.** WebSocket hub — in-memory, один узел; это главное ограничение масштабирования. Realtime не пишет домен (кроме тикетов), хорошо изолируется.

**Решение.** Wave 1: `realtime` + `audit`. До этого — Wave 0 (Kafka, Redis, outbox, контракты).

**Альтернативы.** Начать с media (тоже хороший кандидат, но меньше влияет на доступность), начать с identity (рискованно), начать с chat/message (дорого).

**Последствия.** Нужны ACL-кэш, replay API, per-device envelopes. Зато снимается главное ограничение масштаба и появляется polyglot runtime (WebFlux/Netty).

## ADR-010: Нет общей доменной библиотеки

**Статус:** proposed

**Контекст.** `shared` (3 тыс. LOC) содержит `Principal`, `TenantContext`, ошибки, порты. Соблазн сделать «common» с доменом.

**Решение.** Общая платформа — только security, observability, outbox, тест-утилиты, ошибки транспорта. Доменные классы не шарятся: каждый сервис имеет свою модель. Дублирование DTO допустимо.

**Альтернативы.** Общая доменная библиотека (связанность релизов, «распределённый монолит»), копирование всего (дублирование логики).

**Последствия.** Больше кода/маппинга; зато независимые релизы и чистые границы. Версионирование платформенной библиотеки — по semver.

## ADR-011: Admin — CQRS read model

**Статус:** proposed

**Контекст.** Сейчас admin-контроллеры читают чужие схемы через `SECURITY DEFINER` (`ops.platform_overview`, `admin_users_page`), делают кросс-схемные JOIN. После разделения это невозможно.

**Решение.** `admin` строит проекции из событий (users/chats/storage/overview) в своей БД; списки/фильтры — из read model; команды — через API владельцев данных.

**Альтернативы.** API composition в BFF (N+1, медленно, сложные фильтры), прямой доступ к БД сервисов (запрещён), отдельный DWH (тяжело для оперативных экранов).

**Последствия.** Eventual consistency админки (секунды), необходимость replay/rebuild проекций. Зато нет кросс-БД JOIN и `SECURITY DEFINER`.

## ADR-012: Kubernetes без service mesh на старте

**Статус:** proposed

**Контекст.** Целевая платформа — K8s, 3 AZ. Service mesh (Istio/Linkerd) даёт mTLS, retries, traffic splitting, но добавляет сложность.

**Решение.** K8s + cert-manager для mTLS + NetworkPolicy + Spring Resilience4j. Canary/трафик — через ingress/feature flags. Mesh — позже, при росте числа сервисов/команд.

**Альтернативы.** Сразу mesh (тяжело для небольшой команды), без mTLS (нельзя), VM/bare metal (дороже эксплуатация).

**Последствия.** Часть функций (retry, timeout, circuit breaker) — в коде/библиотеке; единообразие обеспечивается шаблоном сервиса.

## ADR-013: Search — отдельный сервис, только managed

**Статус:** proposed

**Контекст.** Сейчас поиск — SQL по `message`; E2EE нельзя индексировать; нужен OpenSearch и ACL-фильтр.

**Решение.** `search` — отдельный сервис/воркер: потребляет события, индексирует только managed, применяет ACL и DLP-редакцию, отдаёт query API. PostgreSQL не SoT.

**Альтернативы.** Поиск внутри `conversation` (связанность, другой профиль), внешний SaaS (данные/комплаенс), не делать (не соответствует продукту).

**Последствия.** Eventual consistency индекса (lag p95 < 10 с), reindex при смене схемы, стоимость OpenSearch.

## ADR-014: Комнаты остаются в conversation

**Статус:** proposed

**Контекст.** `room` создаёт backing GROUP-чат и `room.rooms` в одной транзакции; presence — live-состояние. Модуль маленький (1,4 тыс. LOC).

**Решение.** Метаданные комнат и жизненный цикл — в `conversation`; live-presence — в `realtime` (Redis). Отдельный сервис не создаётся.

**Альтернативы.** `room` как отдельный сервис (лишняя транзакция с chat), `room` в `realtime` (доменные данные в realtime).

**Последствия.** Меньше сервисов; `conversation` чуть шире. Presence-эндпоинты комнат проксируются в `realtime`.

## ADR-015: Strangler Fig и запрет dual writes

**Статус:** proposed

**Контекст.** Нужно переходить без big bang и без потери данных.

**Решение.** Монолит остаётся; edge маршрутизирует по префиксам; новый сервис забирает трафик поэтапно. Данные — backfill + CDC/outbox, затем переключение. Dual writes запрещены.

**Альтернативы.** Big bang (риск), параллельная работа двух систем с dual write (рассинхрон), заморозка на дни (недопустимо).

**Последствия.** Дольше, но обратимо. Требует фича-флагов, shadow-read, мониторинга расхождений и дисциплины rollback.
