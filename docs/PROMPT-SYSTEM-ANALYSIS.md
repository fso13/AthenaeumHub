## Продукт и стек

«Сова» — приватный мессенджер для команд, семей и закрытых сообществ. Ключевая особенность — два режима в одном продукте:

1. **Конфиденциальный (E2EE):** сервер не читает содержимое сообщений, файлов и стикеров; поиск локальный; серверные плагины недоступны; плагины на клиенте — только с явным согласием пользователя.
2. **Управляемый (managed):** TLS + шифрование на сервере, DLP, антивирус, серверный поиск, журнал аудита, break-glass с подтверждением.

Ограничения стека:

- Java 21, Spring Boot 3.x, PostgreSQL 16, Redis, S3/MinIO, Kafka или NATS JetStream, WebSocket, Keycloak/OIDC.
- Фронтенд: TypeScript/JavaScript, React, WebCrypto/Libsodium.
- Плагины: sandboxed iframe + postMessage RPC, capability-токены, permissions, подпись, allowlist.
- На старте — модульный монолит, а не преждевременные микросервисы.

## Что нужно сделать

Создай **системный анализ (System Analysis / Solution Design)**, а не пересказ бизнес-документа. Каждое бизнес-требование должно превратиться в проверяемое системное поведение: актор → сценарий → API/событие → данные → права → ошибки → тест.

Не расширяй scope: явно разделяй MVP, v1 и v2. Если требование нельзя реализовать в выбранном режиме безопасности — переформулируй его или вынеси в открытые вопросы.

## Обязательные разделы результата

### 1. Резюме для архитектора

Границы системы, ключевые архитектурные решения, 5–7 главных рисков, что входит и что не входит в MVP.

### 2. Контекст и акторы

- Акторы: гость, участник, модератор, админ чата, владелец чата, админ воркспейса, владелец воркспейса, системный администратор, плагин, внешние системы.
- Внешние системы: Keycloak, S3/MinIO, KMS/Vault, Web Push, email, plugin runtime, SIEM.
- Границы доверия: клиент, edge, backend, хранилище, плагин, администратор.
- C4 Level 1 (System Context) и Level 2 (Container) в Mermaid.

### 3. Домен и глоссарий

Единый язык: workspace, membership, chat, message, attachment, sticker pack, sticker, plugin installation, device, key, quota, audit event, invite, break-glass. Для каждого — определение, владелец, жизненный цикл.

### 4. Use cases

Таблица: `UC-ID`, название, актор, триггер, пред-/постусловия, основной поток, альтернативные потоки, связанные FR, приоритет (MVP/v1/v2).

Обязательно покрой:

- регистрацию, приглашение, гостевой доступ;
- создание личного и группового чата;
- отправку, редактирование, удаление, ответ, реакцию;
- смену роли, удаление участника, передачу владения;
- E2EE 1:1 и групповой E2EE;
- загрузку файла с лимитами, квотой и докачкой;
- стикеры: пикер, отправка, свои наборы, модерация;
- установку и включение плагина, отзыв прав;
- проверку ключей, отзыв устройства;
- аудит, DLP и break-glass в managed-режиме.

### 5. Функциональная декомпозиция

Разбей систему на модули/сервисы: auth, workspace, chat, message, realtime, file, sticker, plugin, notification, search, admin/audit. Для каждого:

- ответственность и границы;
- входящие/исходящие события;
- данные, которыми владеет;
- что не делает (anti-scope);
- синхронные и асинхронные зависимости.

### 6. Модель данных

- ERD в Mermaid.
- Таблицы: назначение, ключи, уникальные ограничения, индексы, партиционирование, soft delete, retention.
- Мультитенантность и RLS по `workspace_id`.
- Идемпотентность сообщений (`client_message_id`), порядок (`seq`), read receipts.
- Квоты и лимиты: где хранятся, как резервируются, как освобождаются.
- Ключи и устройства: где хранятся публичные ключи, как отзываются.
- Стикеры: паки, стикеры, установки, недавние, избранное, дедупликация по `sha256`.
- Аудит: append-only, hash chain, экспорт.

### 7. API и реальное время

- REST: метод, путь, назначение, аутентификация, права, request/response, коды ошибок, пагинация, версионирование.
- WebSocket: события, payload, порядок, дедупликация, resume по `last_seq`, поведение при reconnect.
- Единый формат ошибок: `code`, `message`, `details`, `request_id`.
- Для каждого изменяющего endpoint — idempotency key и проверка прав на сервере.
- Отдельно опиши API стикеров, загрузки файлов и плагинов.
- Пример OpenAPI-фрагмента для 5–7 ключевых endpoint’ов.

### 8. Сценарии взаимодействия (sequence)

Mermaid-диаграммы минимум для шести сценариев:

1. Вход, выпуск токенов, регистрация устройства.
2. Отправка E2EE-сообщения 1:1: prekeys → сессия → шифрование → доставка → receipt.
3. Групповой E2EE: sender keys, добавление/удаление участника, ротация.
4. Загрузка файла: preflight → chunk → encrypt → S3 → сообщение → квота.
5. Отправка стикера и загрузка своего набора (валидация, шифрование, модерация).
6. Установка плагина и вызов RPC: permissions → capability token → проверка → аудит.
7. (Опционально) break-glass в managed-режиме и запись в аудит.

Для каждого сценария укажи: участвующие компоненты, синхронные/асинхронные шаги, возможные сбои и компенсации.

### 9. Состояния

State machine в Mermaid для:

- сообщения: создано → отправлено → доставлено → прочитано → изменено/удалено;
- загрузки: init → uploading → paused → scanning → ready / failed / expired;
- участника чата: invited → active → restricted → removed;
- плагина: available → installed → enabled → disabled → blocked;
- набора стикеров: draft → review → active → disabled → removed;
- устройства/ключа: active → rotated → revoked.

### 10. Роли и права

- Матрица workspace-level и chat-level.
- RBAC + проверки на уровне ресурса; где нужен ABAC (гость, E2EE-чат, плагин).
- Отдельно: кто управляет стикерами, кто видит аудит, кто меняет лимиты и квоты, кто включает плагины.
- Правило: UI скрывает недоступное, но сервер проверяет каждое действие независимо.

### 11. Безопасность и E2EE

- Модель доверия и что именно сервер **не** может видеть.
- Ключевая иерархия: identity keys, prekeys, device keys, sender keys, file keys, backup keys.
- Мультидевайсность, восстановление истории, отзыв устройства.
- Шифрование файлов, превью, стикеров; метаданные, которые всё равно видны серверу.
- E2EE и плагины: почему серверные плагины невозможны, как работает клиентский consent.
- Managed-режим: KMS, break-glass, DLP, аудит, кто и как получает доступ.
- Угрозы и контрмеры: MITM, компрометация сервера, злой админ, потеря устройства, вредоносный плагин, вредоносный стикер, фишинг-приглашение, злоупотребление квотами.
- Что мы **не** обещаем (скриншоты, скомпрометированный клиент, анонимность метаданных).

### 12. Файлы, стикеры и лимиты

- Таблица лимитов: Community / Family / Team / Enterprise; один файл, хранилище, число файлов в сообщении, гостевой лимит, срок хранения.
- Preflight: что проверяет клиент, что проверяет сервер, какие коды ошибок (`FILE_TOO_LARGE`, `QUOTA_EXCEEDED`, `TOO_MANY_FILES`, `UNSUPPORTED_TYPE`).
- Chunked upload, resume, идемпотентность, дедупликация, antivirus, E2EE.
- Стикеры: PNG/WebP/APNG, ≤512 КБ, 512×512, запрет SVG, лимиты паков, модерация, квота, кэш.
- Разница между «лимит тарифа» и «демо-лимит прототипа»; сервер — источник истины.

### 13. Плагины

- Манифест, поверхности (panel/composer/message/bot), permissions.
- Sandbox, RPC, capability-токены, TTL, allowlist egress.

- Ограничения по квотам и стоимости хранения.

## Правила анализа

1. **Не пересказывай концепцию.** Превращай требования в поведение, контракты, данные и проверки.
2. **Не выдумывай молча.** Всё неизвестное помечай `[ASSUMPTION]` или `[TBD]`; в конце собери открытые вопросы.
3. **Сервер не читает E2EE.** Не предлагай серверный поиск, серверные плагины или серверный DLP для E2EE-чатов.
4. **Лимиты — серверные.** Клиентская проверка нужна только для UX; сервер обязан отклонить превышение.
5. **Стикеры — медиа, не активный контент.** SVG/HTML/скрипты запрещены.
6. **Права проверяются на каждом действии.** UI-скрытие не считается защитой.
7. **Идемпотентность и порядок** обязательны для сообщений, загрузок и платежей/квот.
8. **MVP ≠ всё.** Если функция из v1/v2, так и помечай.
9. **Ссылайся на источники.** Для каждого раздела — какие FR/BR он закрывает.
10. **Пиши для реализации.** Backend-разработчик должен понять, что и где проверять; QA — что тестировать.

## Критерии готовности

Результат готов, если:

- каждое бизнес-требование прослеживается до сценария, API/события, сущности и теста;
- у каждого API есть права, ошибки, идемпотентность и лимиты;
- E2EE-граница описана честно и без противоречий;
- файлы и стикеры описаны end-to-end, включая лимиты, квоты и отказы;
- роли и права проверяемы на сервере;
- есть C4, ERD, минимум 6 sequence-диаграмм и состояния;
- MVP отделён от v1/v2;
- backend- и QA-команды могут начать декомпозицию без дополнительного пересказа.
